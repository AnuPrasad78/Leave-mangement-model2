# Leave Portal — Issues & Fixes (2026-10-05)

## 1. Login refused every attempt ("Invalid credentials")

**Cause** — Supabase Auth had zero users. The demo-user seed script was never run, and it was broken anyway: `admin.auth.createUser` no longer exists in supabase-js v2 (it is `auth.admin.createUser`).

**Fix** — corrected + ran `scripts/seed-users.mjs`; created and verified both demo accounts
(`sai.nithinreddy@emids.com` — manager, `sandeep.venkateshkamath@emids.com`, password `Portal@2026`).

## 2. Leave request silently failed to submit

**Cause A — RLS infinite recursion (the root blocker).** The `employees_select` policy sub-queried `employees` from inside its own policy → Postgres `42P17 infinite recursion` → **every** authenticated query failed with 500, including the "who am I" profile fetch → the app ran with no employee id → the submit path bailed out before inserting, with no visible error.

**Fix A** — `supabase/patch-002-policy-recursion.sql`: no sub-selects in a table's own policy; scope expressed with row-column checks plus a new SECURITY DEFINER helper `auth_manager_id()`. Same fix baked into `supabase/schema.sql` for fresh databases.

**Cause B — FK hint mismatch.** The manager-name embed referenced constraint `employees_manager_id_fkey`, which does not match the live DB's constraint name.

**Fix B** — dropped the explicit hint; the `employees→employees` relationship is unambiguous (`src/store/AuthContext.jsx`).

**Cause C — empty leave-type list.** `setLeaveTypes` was never called, so the Apply form rendered no leave-type chips.

**Fix C** — `loadLeaveTypes()` added to the session load in `AuthContext`.

**Verified** — request `LV-10319` (PTO, 13–15 Oct, 3 days, Pending) submitted end-to-end.

## 3. Leave could be requested for past dates

**Fix** — three layers:

1. From-date picker cannot be picked before today (`min` attribute on the input).
2. Submit-time validation: "Leave cannot start in the past."
3. `supabase/patch-003-no-backdated.sql` — BEFORE-INSERT trigger on `leave_requests`; only JWT sessions are checked (`auth.uid() is not null`), so seed data's historical rows still insert.
